# Fintris 기능명세서

목적별 자금 관리 서비스 · 1팀 이거해조 · 2026-10-25 기준 (주간보고서 10/21까지 반영, 불규칙 수입은 에이전트 대화로 처리하기로 결정)

## 읽는 법

- ID 접두사: **F** 제안서의 기능, **N** 주간보고서에서 새로 정해진 기능, **C** 기능이 아닌 공통 기반
- 우선순위: **핵심** 소비 분석 → 블록 → 절약 → 목표 흐름에 꼭 필요한 기능, **부가** 그 위에 얹는 기능
- 계산은 BE가 하고, AI는 분류·설명·대화만 한다. AI 출력의 숫자는 계산 결과와 맞는지 검증한다.
- 돈과 관련된 실행(배분·이동·블록 저장)은 항상 미리보기 후 사용자 확인으로 반영한다. 실제 이체는 하지 않는다.
- 구독제(유료 플랜)는 없다.
- 기능 파일에서 "먼저 필요한 것"이 끝나야 그 기능을 구현할 수 있다.

## N-01 로그인·온보딩

- 우선순위: **핵심** (앱을 쓰기 시작하는 입구)
- 구분: 시작하기
- 담당·일정: BE 로그인·JWT·동의·온보딩 API (S2~S3) · FE 로그인·회원가입 화면
- 현재 상태 (10/21 보고서): 로그인·JWT 완료, 동의·온보딩 API 개발 중
- 먼저 필요한 것: C-01 DB 스키마·ERD, C-02 개발·배포 환경
- 이걸 해야 가능한 것: N-02 계좌 연동, F-04 블록 생성·규칙

### 한 줄 설명

회원가입, 동의, 프로필 입력까지 앱을 쓰기 시작하는 입구.

### 요구사항

- N-01-1 카카오·Gmail·로컬 로그인을 지원한다.
- N-01-2 약관·개인정보 동의 이력을 저장한다.
- N-01-3 프로필을 입력받고 동의 이력·사용자 설정을 분리해 저장한다.
- N-01-4 가입이 끝나면 곧바로 계좌 연동(N-02)으로 이어진다.

### 수용 기준

가입 → 동의 → 프로필 → 계좌 연동 화면까지 끊김 없이 이동한다.

## N-02 계좌 연동

- 우선순위: **핵심** (모든 기능이 쓰는 거래 데이터의 출처)
- 구분: 시작하기
- 담당·일정: BE 거래 저장·조회 API, CODEF 연동 (S2~S3)
- 현재 상태 (10/21 보고서): CODEF 샌드박스 연동 완료, 데모 버전 발급·키 연결, 개발용 EC2 고정 IP 허용 확인
- 먼저 필요한 것: N-01 로그인·온보딩, C-02 개발·배포 환경
- 이걸 해야 가능한 것: N-03 초기 블록 배치·튜토리얼, F-01 소비 분석·분류, N-05 신용카드, N-06 더치페이, N-07 불규칙 수입 대응

### 한 줄 설명

CODEF로 은행 계좌·거래 내역을 가져온다. 블록과 AI 에이전트가 쓸 거래 데이터의 출발점.

> 다른 은행 동시 연동·계좌 선택·호출 제한은 미검증. 구조를 유연하게 설계

### 요구사항

- N-02-1 ✅ 회원가입 직후 계좌 연동을 필수로 진행한다.
- N-02-2 ✅ 연동된 모든 계좌를 메인에서 합산해 보여준다.
- N-02-3 ✅ 상단 은행 카드를 스와이프하면 은행별 거래 내역을 볼 수 있다. 메인 블록 구성은 그대로 둔다.
- N-02-4 거래 내역은 하루 1회와 앱 실행 시 조회하고, 변경분만 가져온다(증분 동기화).
- N-02-5 금융기관 인증정보는 저장하지 않고 CODEF connectedId로 조회한다.

### 규칙 · 예외 · 기타

#### 규칙 · 예외
- 한 은행을 연동하면 그 은행의 여러 계좌가 함께 조회된다 (확인됨).
- 조회 실패 시 마지막 동기화 시각을 보여주고 저장된 데이터로 계속 동작한다.

### 수용 기준

시드 또는 샌드박스 거래가 저장되고 홈 조회 API로 합산 금액이 나온다.

### 🔶 결정 필요

- 다른 은행 동시 연동·특정 계좌만 선택하는 방법·API 호출 제한 (검증 필요)
- 분석 소요 시간 동안 분류 전 화면을 어떻게 보여줄지

<a id="n-03"></a>

## N-03 초기 블록 배치·튜토리얼

- 우선순위: **핵심** (블록을 처음 채우는 첫 사용 경험)
- 구분: 시작하기
- 담당·일정: AI 거래 분석·구성안 · BE 블록 저장 · FE 튜토리얼·블록 확인 화면
- 먼저 필요한 것: N-02 계좌 연동, F-01 소비 분석·분류, F-04 블록 생성·규칙
- 이걸 해야 가능한 것: F-11 블록 시각화·상태, F-10 일별 생활비 가이드

### 한 줄 설명

계좌 연동 직후 AI가 거래를 분석해 첫 블록을 배치한다. 분석을 기다리는 동안 마스코트가 기능을 안내한다.

### 요구사항

- N-03-1 ✅ 처음부터 세부 블록을 나누지 않는다.
- N-03-2 ✅ 거래로 명확히 판단되는 고정지출(월세·구독료 등)을 먼저 분류한다.
- N-03-3 ✅ 식비·교통비 등은 생활비 범주로 묶는다.
- N-03-4 ✅ 여행비·비상금·저축처럼 거래만으로 목적을 알 수 없는 블록은 사용자가 직접 추가·조정한다.
- N-03-5 ✅ 튜토리얼은 모든 사용자에게 같은 목업 데이터로 보여준다. 분배 미완료 상태와 오류 처리 부담을 줄이기 위해서다.
- N-03-6 구성안은 미리보기로 보여주고 사용자가 수정·저장해야 반영된다.

### 규칙 · 예외 · 기타

#### 흐름
1. 계좌 연동 완료
2. AI가 거래 내역 분석 (이 동안 목업 데이터로 마스코트 튜토리얼)
3. 실제 거래 기반 블록 구성 확인
4. "시작하기"로 메인 진입

마스코트: 불꽃 캐릭터가 유력(단순한 형태, 상태별 색 변화). 장식이 아니라 소비 상황에 따라 표정이 바뀌고 온보딩을 안내한다. 최종 결정은 시안 후 투표.

예외: 분석이 실패하거나 반복 결제가 없으면 기본 템플릿(생활비·비상금)만 제안한다.

### 수용 기준

시드 페르소나에서 월세·통신비가 고정지출 블록으로 제안되고, 저장 전에는 블록이 만들어지지 않는다.

### 🔶 결정 필요

- 분석 결과를 사용자가 수정하는 방법

## F-04 블록 생성·규칙

- 우선순위: **핵심** (블록과 목표가 서비스의 중심)
- 구분: 블록
- 담당·일정: BE 블록 API (S2), 상세·규칙 저장 (S3) · AI 구성안 설명 (S4) · FE 블록 화면 (S2)
- 현재 상태 (10/21 보고서): 블록 CRUD·순서 변경·카테고리 연결 API 머지 (PR #9)
- 먼저 필요한 것: C-01 DB 스키마·ERD, N-01 로그인·온보딩, F-01 소비 분석·분류
- 이걸 해야 가능한 것: N-03 초기 블록 배치·튜토리얼, F-07 목표 관리, F-11 블록 시각화·상태, F-06 이동 전 검증, F-05 절약 금액 배분, N-07 불규칙 수입 대응, F-10 일별 생활비 가이드, F-09 이상 징후 감지, F-16 대화형 코치

### 한 줄 설명

목적·금액·기간·규칙·상태를 가진 자금 관리 단위. 사용형·목표형·고정지출형 세 유형이 있다.

> 직접 만드는 CRUD는 거래 없이 가능. 자동 제안(F-04-3~5)만 F-01·N-03이 필요

### 요구사항

- F-04-1 세 유형을 만들고 수정·삭제할 수 있다.
- F-04-2 유형별 필수값을 받는다 (목표형: 목표 금액·기한 / 고정지출형: 납부일·납부액).
- F-04-3 반복 결제를 탐지해 고정지출 블록 후보와 규칙(금액·납부일)을 제안한다.
- F-04-4 같은 사람에게 매달 비슷한 금액을 보내는 송금(월세·관리비)도 반복 결제로 본다.
- F-04-5 제안은 미리보기 후 사용자가 저장해야 반영된다. 초기 배치는 N-03을 따른다.

### 규칙 · 예외 · 기타

#### 유형
- 사용형(생활비): 월 단위 기간, 남은 기간 기준 일별 사용 가능 금액. 계좌 연동 시 자동 생성
- 목표형(여행·비상금·저축): 목표 금액, 기한, 월 확보 금액. 사용자 생성
- 고정지출형(월세·통신비·공과금·보험료): 납부일, 납부액, 납부 전 확보 여부. AI 제안 또는 사용자 생성

#### 규칙 · 예외
- 고정지출 탐지: 같은 가맹점(수취인) 3회 이상, 금액 편차 10% 이내, 날짜 편차 3일 이내
- 블록 배분 합계는 연동 계좌 합산 잔액을 넘을 수 없다.
- 잔액이 있는 블록을 지우면 남은 금액을 옮길 블록을 고르게 한다.

### 수용 기준

시드 데이터에서 반복 결제가 고정지출 후보로 제안된다.

### 🔶 결정 필요

- 미배분 잔액을 별도 블록으로 보여줄지
- 블록 최대 개수

- 담당·일정: FE 시각화 (S2~) · BE 상태 판정 (일정상 S5)
- 현재 상태 (10/21 보고서): 홈 조회 API 리뷰 중(PR #10), FE 홈 화면 구현 착수
- 먼저 필요한 것: F-04 블록 생성·규칙, F-07 목표 관리, N-03 초기 블록 배치·튜토리얼
- 이걸 해야 가능한 것: F-06 이동 전 검증, N-05 신용카드, F-14 금융관리 점수

### 한 줄 설명

배분 금액에 비례한 블록 크기와 안전·주의·위험 상태 태그, 목표 채움으로 자금 상태를 한눈에 보여준다.

> F-11-5(상태 변화 AI 설명)는 F-09 이후에 연결

### 요구사항

- F-11-1 메인에 블록을 테트리스형으로 배치하고 크기는 배분 금액에 비례한다.
- F-11-2 블록마다 상태 태그를 표시한다.
- F-11-3 목표형 블록은 달성률만큼 채워 보여준다.
- F-11-4 거래·배분·이동이 일어나면 잔액과 상태를 다시 판정한다.
- F-11-5 상태가 바뀌면 AI가 이유와 대안을 설명한다.

### 규칙 · 예외 · 기타

디자인 결정 ✅ 메인 배경은 흰색, 연두색은 강조 요소에만, 블록 색상은 약 10색 팔레트로 제한

#### 상태 판정 (서버 로직, AI 아님)
- 고정지출형: 납부일 전 납부액 확보 → 안전 / 부족 예상 → 주의 / 확보 어려움 → 위험
- 사용형: 기간 경과율 대비 사용률
- 목표형: 이번 달 월 확보 금액 충족 여부

예외: 작은 블록도 터치할 수 있는 최소 크기 · 판정 데이터가 없으면 "-"

### 수용 기준

같은 입력이면 항상 같은 판정이 나온다 (단위 테스트).

### 🔶 결정 필요

- 주의·위험을 가르는 수치 기준
- BE 판정을 S4로 당길지

## F-06 이동 전 검증

### 한 줄 설명

> 일정 조정안: S3에는 고정지출 납부 가능 여부 계산만 먼저 구현, 전체 판정은 F-11(BE)과 함께

### 규칙 · 예외 · 기타

- 잔액보다 큰 금액은 이동할 수 없다. 검증 후 잔액이 바뀌었으면 다시 검증한다.

### 수용 기준

검증 결과와 실제 이동 결과가 같고, 오류가 나면 두 블록 모두 원래대로 돌아간다.

### 🔶 결정 필요

- 규칙을 깨는 이동을 막을지, 경고만 하고 허용할지

거래를 카테고리로 분류하고 카테고리별 지출, 반복 소비, 전월 대비 변화를 보여준다.

- F-01-3 같은 가맹점의 반복 소비를 찾는다.

## N-06 더치페이

- 우선순위: **부가** (결정: 필수 기능이 아닌 차별화 요소)
- 구분: 거래 분석·입력

- 이걸 해야 가능한 것: 없음

### 요구사항

- N-06-1 결제 건에 [1/N]을 눌러 본인 몫만 소비로 기록한다.
- N-06-2 정산 입금을 해당 결제와 연결해 수입에서 제외한다.

- N-06-4 연동 계좌를 합산하면 정산금을 다른 계좌에 둔 경우에도 흐름을 파악할 수 있다(N-02).

### 규칙 · 예외 · 기타

배경: 한 번에 결제하면 전체 금액이 지출, 받은 정산금이 수입으로 잡힌다. 정산 시점이 제각각이고 정산금을 카카오페이 등에 보관하기도 한다.

결정 ✅ 결제 건에서 [1/N]을 누르고 정산 입금을 연결하는 방식. 필수 기능이 아니라 차별화 요소이며 세부 구현 범위는 추가 검토.

검토 중: 입출금을 노드로 보고 관련 거래를 연결하는 구조 (구현 가능성·난이도 미검토)

## F-15 맥락 확인 질문

- 우선순위: **핵심** (분류와 절약 제안의 정확도를 높이는 AI 에이전트의 중심 기능)
- 구분: 거래 분석·입력
- 담당·일정: AI 질문 판단·문장 (S4) · BE 태그 저장·푸시 (S4) · FE 질문 화면·푸시 버튼 (S4)
- 먼저 필요한 것: F-01 소비 분석·분류, C-05 AI 서버·에이전트 루프, C-06 푸시 발송·알림 설정
- 이걸 해야 가능한 것: N-06 더치페이, F-02 절약 후보·제안, F-14 금융관리 점수

### 한 줄 설명

결제처만으로 알 수 없는 거래를 푸시로 묻고, 답을 태그로 저장해 분류와 절약 제안에 반영한다.

### 요구사항

- F-15-1 Jeff가 거래마다 자동 처리할지 질문할지 판단한다.
- F-15-2 질문 문장은 자체 서버 sLM이 만든다.
- F-15-3 푸시의 버튼 한 번 또는 대화로 답한다.
- F-15-4 자유 답변은 태그로 분류하고 태그만 저장한다 (대화 원문은 최소 저장).
- F-15-5 같은 패턴에 같은 답이 반복되면 규칙으로 저장하고 다시 묻지 않는다.
- F-15-6 반복 송금(같은 사람, 매달 비슷한 금액)은 묻지 않는다.

### 규칙 · 예외 · 기타

#### 질문 유형
- 소비 이유 (밤 11시 배달 앱) → [야근·업무] [친구·약속] [그냥 먹고 싶어서]. 야근·업무는 불가피한 지출이라 절약 후보에서 뺀다.
- 구매 품목 (쿠팡·간편결제) → [생필품] [식비] [의류] [기타]
- 개인 간 이체·현금 → [더치페이] [선물·경조사] [빌려준 돈] [기타]

예외: 답하지 않은 질문은 확인 목록에 두고 일정 기간 후 기본 분류로 처리 · 자체 서버 장애 시 템플릿 질문 또는 에이전트 오프라인

### 수용 기준

"야근·업무"로 답한 거래가 절약 후보에서 빠지고, 발송·응답 이력이 저장된다 (에이전트 응답률 측정용).

### 🔶 결정 필요

- 규칙 저장 반복 횟수와 "같은 패턴" 정의
- 하루 최대 질문 수

<a id="f-02"></a>

## F-02 절약 후보·제안

- 우선순위: **핵심** (절약 → 배분으로 이어지는 핵심 흐름)
- 구분: 절약
- 담당·일정: AI 후보 탐지·문장 (S3) · FE 제안 카드 (S3) · BE 수락·수정·제외 API (S4)
- 먼저 필요한 것: F-01 소비 분석·분류, F-15 맥락 확인 질문, F-07 목표 관리
- 이걸 해야 가능한 것: F-03 절약 금액 계산

### 한 줄 설명

평소보다 늘었거나 반복되는 지출을 후보로 보여주고 "배달을 주 2회 줄이면 월 약 6만 원"처럼 행동과 금액으로 제안한다. 무엇을 줄일지는 사용자가 고른다.

> 일정 조정안: S3는 불가피 지출 제외 없이 제안, S4에 F-15 연동

### 요구사항

- F-02-1 증가했거나 반복되는 지출을 후보로 뽑는다.
- F-02-2 불가피로 확인된 거래(야근 식대 등)는 제외한다.
- F-02-3 후보마다 절약 행동과 예상 금액을 카드로 보여준다.
- F-02-4 수락·수정·제외할 수 있고, 수락하면 절약 목표가 된다.
- F-02-5 수락하면 목표 단축 효과를 함께 보여준다 (예: "여행 블록 목표가 1개월 앞당겨져요").

### 규칙 · 예외 · 기타

#### 규칙 · 예외
- 예상 절약 금액 = 1회 평균 지출 × 줄이는 횟수 × 기간 환산. 계산은 BE, AI는 문장만 만든다.
- 이력이 1개월 미만이면 반복 소비 기준으로만 제안한다. 문장 생성이 실패하면 템플릿 문장으로 대체한다.

### 수용 기준

문장 속 금액이 계산 결과와 같고, 불가피 태그가 붙은 거래는 후보에 없다.

### 🔶 결정 필요

- "평소보다 늘었다"의 기준
- 한 번에 보여줄 카드 수

## F-03 절약 금액 계산

- 우선순위: **핵심** (절약 → 배분으로 이어지는 핵심 흐름)
- 구분: 절약
- 담당·일정: BE 계산 (S4) · FE 확인 화면 (S3)
- 먼저 필요한 것: F-02 절약 후보·제안
- 이걸 해야 가능한 것: F-05 절약 금액 배분, F-14 금융관리 점수, F-12 월간 리포트

### 한 줄 설명

절약 목표를 정하면 확보할 금액을 계산하고, 기간이 끝나면 실제 지출과 비교해 확정한다.

### 요구사항

- F-03-1 절약 목표별 예상 금액을 보여준다.
- F-03-2 기간 중 실제 지출을 추적해 진행 상황을 보여준다.
- F-03-3 기간이 끝나면 절약 금액을 확정한다.
- F-03-4 확정 금액은 배분 대기 상태로 두고 F-05로 넘긴다.

### 규칙 · 예외 · 기타

#### 규칙 · 예외
- 확정 절약 금액 = max(0, 기준 지출 − 실제 지출). 기준 지출은 제안 시점의 과거 평균.
- 실제 지출이 더 많으면 0원으로 확정하고 초과분은 리포트에 기록한다. 기간 중 분류가 바뀌면 다시 계산한다.

### 수용 기준

확정 금액이 수작업 계산과 같다 (테스트 케이스 포함).

### 🔶 결정 필요

- 절약 기간 단위(월·주)
- 절약한 돈을 이미 써버린 경우의 처리

## F-05 절약 금액 배분

- 우선순위: **핵심** (절약 → 배분으로 이어지는 핵심 흐름)
- 구분: 절약
- 담당·일정: BE 반영·달성률 갱신 (S4) · FE 배분 화면 (S3)
- 먼저 필요한 것: F-03 절약 금액 계산, F-04 블록 생성·규칙, F-07 목표 관리
- 이걸 해야 가능한 것: F-08 목표 달성 지원, F-14 금융관리 점수, F-12 월간 리포트

### 한 줄 설명

확정된 절약 금액을 여행·비상금·저축 같은 목적 블록에 배분해 목표에 쌓이게 한다.

> FE는 BE API(S4)보다 먼저 목업 응답으로 화면 구현

### 요구사항

- F-05-1 배분 대기 금액과 배분할 수 있는 블록을 보여준다.
- F-05-2 배분 전 잔액·달성률·달성 예상 시점을 미리 보여준다.
- F-05-3 확인하면 반영하고 목표형 블록의 달성률을 갱신한다.
- F-05-4 배분 이력을 남긴다.

### 규칙 · 예외 · 기타

배분 방식: 직접 선택 · 비율 자동 · AI 제안 (배분안 계산은 BE, 설명은 AI)

예외: 합계가 대기 금액을 넘으면 저장할 수 없다. 목표 금액을 넘는 배분은 초과분을 안내하고 다른 블록을 권한다.

### 수용 기준

배분 후 블록 잔액 변화의 합이 배분 금액과 같다.

### 🔶 결정 필요

- 배분하지 않은 절약 금액의 보관 기간과 처리

## F-07 목표 관리

- 우선순위: **핵심** (블록과 목표가 서비스의 중심)
- 구분: 목표
- 담당·일정: BE 달성률 계산 (S2) · FE 목표 설정 화면 (S3)
- 먼저 필요한 것: F-04 블록 생성·규칙
- 이걸 해야 가능한 것: F-11 블록 시각화·상태, F-02 절약 후보·제안, F-05 절약 금액 배분, F-08 목표 달성 지원, F-16 대화형 코치

### 한 줄 설명

목표형 블록의 목표 금액·기한을 정하고 달성률과 남은 금액을 보여준다.

### 요구사항

- F-07-1 목표 금액, 기한, 월 확보 금액을 설정·수정한다.
- F-07-2 달성률, 남은 금액, 달성 예상 시점을 보여준다.
- F-07-3 목표를 달성하면 완료 상태로 바꾸고 알린다.

### 규칙 · 예외 · 기타

#### 계산
- 달성률 = 현재 금액 ÷ 목표 금액 × 100
- 권장 월 확보 금액 = (목표 금액 − 현재 금액) ÷ 남은 개월 수
- 달성 예상 시점은 최근 월평균 적립액 기준

예외: 기한이 지났는데 미달이면 "기한 경과"로 표시하고 기간 변경을 제안한다. 적립 이력이 없으면 권장 월 확보 금액만 보여준다.

### 수용 기준

배분·이동 직후 달성률이 바로 갱신된다.

## F-08 목표 달성 지원

- 구분: 목표
- 담당·일정: BE 부족·월 목표 계산, 배분 제안 로직 (S5) · AI 제안 문장
- 먼저 필요한 것: F-05 절약 금액 배분, F-06 이동 전 검증, F-07 목표 관리, C-06 푸시 발송·알림 설정

### 요구사항

- F-08-4 제안을 실행할 때는 이동 전 검증(F-06)을 거쳐 확인 후 반영한다.

### 수용 기준

제안한 대안을 적용하면 달성 예상 시점이 기한 안으로 들어온다.

### 🔶 결정 필요

## N-07 불규칙 수입 대응

- 우선순위: **부가** (결정: 별도 화면 없이 에이전트 대화로 처리. 에이전트(F-16) 위에 얹는 기능)
- 구분: 알림·가이드
- 현재 상태 (10/21 보고서): 이건하(BE)가 계산식 설계안을 작성했다.
- 먼저 필요한 것: N-02 계좌 연동, F-01 소비 분석·분류, F-04 블록 생성·규칙, F-16 대화형 코치
- 이걸 해야 가능한 것: 없음

### 한 줄 설명

수입이 들쭉날쭉한 사용자를 위해 "월"이 아니라 "수입이 들어온 시점부터 다음 수입까지"를 기준으로 자금을 관리한다. 별도 화면 없이 에이전트와 대화하며 예상 수입을 알려주는 방식으로 푼다.

> F-10·F-09는 이 기능 없이도 동작한다 (월 단위 기본 계산). 수입 일정이 입력되면 다음 수입일 기준으로 바뀐다.

### 요구사항

- N-07-1 별도 화면 없이 에이전트와의 대화로 예상 수입(금액·시기)을 입력받는다.
- N-07-2 수입이 들어온 시점부터 다음 수입 시점까지를 한 기간으로 보고 일별 사용 가능 금액(F-10)을 계산한다.
- N-07-3 수입 금액과 주기를 함께 보고 블록별 분배 조정안을 제안한다. 반영은 사용자가 수락한 뒤에 한다.

### 규칙 · 예외 · 기타

#### 결정
- ✅ 별도 입력 화면이나 설정 메뉴를 만들지 않고 에이전트 대화로 처리한다 (10/25 결정).

#### 계산
- 계산은 BE가 한다. 이건하(BE)가 작성한 계산식 설계안을 쓴다.
- 예: 용돈 35만 원(1일), 아르바이트 31~63만 원(10일), 월세 38만 원이 1일에 빠짐. 월말 잔액이 3만 원이면 10일까지 9일을 버틸 수 있는지가 핵심이다.

#### 예외
- 예상 수입 정보가 없으면 F-10의 기본 계산(월 단위)을 그대로 쓴다.

### 수용 기준

에이전트에게 "10일에 알바비 31~63만 원 들어와"처럼 말하면 다음 수입일까지를 기준으로 일별 사용 가능 금액이 바뀐다.

### 🔶 결정 필요

- 예상 수입을 못 맞춘 달의 보정 방식

## F-10 일별 생활비 가이드

- 우선순위: **핵심** (월말 부족을 미리 막는 핵심 가치)
- 구분: 알림·가이드
- 담당·일정: BE 계산 (S2) · FE 화면 (S4) · AI 안내 문장
- 먼저 필요한 것: F-04 블록 생성·규칙, C-06 푸시 발송·알림 설정, N-03 초기 블록 배치·튜토리얼
- 이걸 해야 가능한 것: F-09 이상 징후 감지

### 한 줄 설명

사용형 블록 잔액과 남은 일수로 오늘 쓸 수 있는 금액을 알려준다.

> 수입 일정이 입력되면(N-07) 다음 수입일까지를 기준으로 계산한다. 입력이 없으면 월 단위로 계산한다.

### 요구사항

- F-10-1 메인에 "오늘 쓸 수 있는 돈"을 표시한다.
- F-10-2 사용자가 정한 시간에 매일 푸시로 알린다.
- F-10-3 오늘 지출이 반영되면 금액을 갱신한다.

### 규칙 · 예외 · 기타

계산: 오늘 쓸 수 있는 금액 = 사용형 블록 잔액 ÷ 남은 일수 (오늘 포함)

예외: 잔액이 0 이하면 0원으로 표시하고 이상 감지(F-09)와 연결한다.

### 수용 기준

월말·월초 경계에서 남은 일수가 정확하다.

### 🔶 결정 필요

- 월 시작일(1일 · 월급일)
- 오늘 쓴 금액을 빼서 보여줄지

- 우선순위: **핵심** (월말 부족을 미리 막는 핵심 가치)

- F-09-2 몬테카를로 시뮬레이션으로 월말 부족 확률을 계산한다.

### 규칙 · 예외 · 기타

감지 대상: 사용형 블록의 빠른 소진 · 납부일 전 고정지출 확보 어려움 · 목표형 블록의 월 확보 금액 부족

예외: 이력이 부족하면 단순 규칙(잔액 < 남은 고정지출 합계)으로 판정한다. AI 설명이 실패하면 템플릿 문장으로 보낸다.

### 수용 기준

중간발표 시연에서 시드 페르소나 기준으로 경보가 발송된다.

### 🔶 결정 필요

- 발송 기준 확률
- S5 이후 경보 기준(서버 판정 vs AI 확률)

## F-16 대화형 코치

- 우선순위: **부가** (핵심 흐름 위에 얹는 기능. 제안서 기준 최종발표(P1) 목표)

- 담당·일정: AI 에이전트 (S5) · FE 대화 화면 (S4 목업 → S5 통합) · BE 도구용 API
- 현재 상태 (10/21 보고서): 에이전트 기본 실행 루프와 도구 호출 루프 테스트 완료. 행동 평가 중이며 비합리적인 행동 패턴이 보여 구조 변경 중
- 먼저 필요한 것: F-04 블록 생성·규칙, F-06 이동 전 검증, F-07 목표 관리, F-08 목표 달성 지원, C-05 AI 서버·에이전트 루프, C-07 AI 숫자 검증·템플릿 폴백, C-08 Gemini 연동
- 이걸 해야 가능한 것: N-07 불규칙 수입 대응

### 한 줄 설명

"이번 달 왜 돈이 부족해?", "여행 자금 언제 다 모여?" 같은 질문에 블록·이동 시뮬레이션 결과로 답하고, 대화로 블록을 만들거나 고친다.

### 요구사항

- F-16-1 의도를 파악해 도구(블록 조회, 소비 집계, 이동 검증, 목표 계산)를 호출하고 그 결과로 답한다.
- F-16-2 블록 생성·수정·이동은 제안 카드로 보여주고 사용자가 수락해야 반영한다.
- F-16-3 간단한 대화는 자체 서버, 어려운 추론은 Gemini로 Jeff가 나눠 보낸다.
- F-16-4 Gemini에는 금액·카테고리·블록 이름만 전달한다.
- F-16-5 답변 속 숫자는 도구 결과와 맞는지 검증한다.

### 규칙 · 예외 · 기타

#### 에이전트 적용 범위 ✅ (10/16 회의)
- 자연어 블록 관리: 금액·설정 변경, 블록 간 자금 이동
- 거래 자동 분류 (F-01)
- 이상 거래 확인 알림 (F-09, F-15)
- 금융 상담
- 장기 메모리 기반 개인화

#### 추후 검토
- 장기 메모리: 한 작업 안에서 쓰는 단기 메모리와 여러 작업에 걸쳐 사용자 정보를 쌓는 장기 메모리를 구분한다. 장기 메모리 구조는 추가 설계가 필요하다.
- 사용자와의 관계에 따라 말투를 조정하는 아이디어

예외: 금융상품 추천·투자 조언은 범위 밖임을 안내한다. 도구 호출이 실패하면 이유를 알리고 관련 화면으로 연결한다.

### 수용 기준

질문 → 도구 호출 → 제안 → 수락 → 블록 반영이 시연에서 끝까지 동작한다.

- 대화 기록 보관 기간
